Production AI in Rails is mostly background‑job engineering

What 12 merged pull requests across ActiveAgent and Lewsnetter taught me about atomic claims, expiring leases, server-side tool approvals, and replayable evals.

    Most demos of AI in Ruby on Rails fail in a boring way once real traffic arrives. It is rarely the prompt. It is a queue that delivers a job twice, a worker that holds a stale record, a scheduled job whose conditions changed while it sat in the queue, or an agent whose only guardrail against deleting customer data was a sentence in the system prompt.

    Between 29 September and 24 November 2026 I had 60 pull requests merged across two open-source Rails codebases: ActiveAgent, a Rails framework for building and evaluating AI agents, and Lewsnetter, a Rails newsletter and email-marketing app with an in-app AI agent and an MCP server. Twelve of those pull requests, six in each repository, attack the same underlying problem: making asynchronous, tool-calling AI workflows behave predictably when queues redeliver, users click cancel, and models improvise.

    Twelve merged pull requests across ActiveAgent (6) and Lewsnetter (6). Almost every failure was classic Rails background-job and authorization engineering made costlier by LLM calls and side-effecting tools: atomic state claims, expiring leases, revalidation at claim time, server-side tool guardrails, and complete eval capture.

    Why AI amplifies ordinary Rails job bugs

    Don't assume a job runs exactly once. In these pull requests the duplicates came from ordinary causes: a queue delivering the same job again, or two workers picking up the same pending row at once. When an ordinary job runs twice, you might recompute a counter or send a duplicate notification. When an AI workflow job runs twice, it pays for a second model generation, fires the agent's tools a second time, or corrupts an evaluation run's score.

    The twelve fixes sit across four places where a Rails app hands work between a user, a queue, a database, and a language model:

    Queues deliver jobs more than once, and LLM calls are slow and side-effecting. The 12 PRs guard four boundaries: atomic state claims, expiring leases for slow provider calls, claim-time revalidation and scoping, and server-side tool guardrails plus eval capture.

    Claim state atomically, never check-then-act ActiveAgent #664 · #672 · #713 · Lewsnetter #61

    A common concurrency bug in Rails jobs looks harmless in code review:

    run = AgentRun.find(run_id)
return if run.finished? || run.awaiting_input?
run.update!(status: :running, started_at: Time.current)

    Before ActiveAgent #664, that was AgentExecutionJob#perform. It had two gaps. First, it checked in Ruby and wrote in SQL as two separate steps: two workers that both loaded the run while it was pending both passed the check and started a generation. Second, it only rejected finished and paused runs, so a duplicate delivery arriving while the run was already running started a second provider call and overwrote started_at.

    Checking run.pending? in Ruby and then calling update! lets two workers pass the check and run the agent twice. Replace check-then-act with one conditional UPDATE ... WHERE id = ? AND status = pending so the database decides at the write. The pull requests tested this on SQLite under Rails 7.2 and 8; #664 also probed it on PostgreSQL 17.

    The fix moves the predicate into a single SQL statement:

    def claim_pending(run)
  now = Time.current
  claimed = AgentRun.where(id: run.id, status: AgentRun.statuses[:pending])
    .update_all(status: AgentRun.statuses[:running], started_at: now, updated_at: now)
  return false if claimed.zero?

  run.reload
  run.broadcast_update
  true
end

    There is a subtle Rails-on-SQLite lesson buried inside #664. My first commit on that branch used run.with_lock instead of a conditional update_all. CI on the rails7.gemfile matrix caught why that wasn't good enough: SQLite under Rails 7.2 opens deferred transactions, so when two workers overlap inside with_lock, the loser's write after its read is refused once the winner commits, raising SQLite3::BusyException instead of quietly declining. A single conditional UPDATE lets the database decide at the write. On SQLite under Rails 7.2 and 8, the second worker waits for the write lock and then matches no row; a standalone probe of the same statement on PostgreSQL 17 claimed once in each of 50 forced races. I didn't test MySQL. The update holds no transaction open while the LLM runs. Because update_all skips Active Record callbacks, the helper reloads the row and calls broadcast_update explicitly.

    Once you spot check-then-act in one place, look for its siblings. The exact same pattern turned up three more times:

    • Cancellation (ActiveAgent #672): AgentRun#cancel! checked its in-memory copy and wrote cancelled unconditionally. If the worker finished between the controller's load and the write, a completed run became cancelled while keeping its output, and a failed run's real error was overwritten with "Cancelled by user". The cancel is now one conditional update_all limited to CANCELLABLE_STATUSES (pending, running, awaiting input), in the same transaction that cancels the run's pending input requests. An earlier fix for issue #377 kept a result from overwriting a cancel; #672 closes the other direction, a cancel overwriting a result.
    • Evaluation runs (ActiveAgent #713): EvaluationRunJob checked run.pending? while ScenarioEvaluationRunner#call wrote running later. A duplicate delivery replayed the entire eval suite or, with fan-out on, enqueued a second full set of replay jobs. Moving a conditional claim! to the top of ScenarioEvaluationRunner#call covered every caller and also fixed a second bug where an error resolving scenario selection left the run stuck in pending forever.
    • Campaign sends (Lewsnetter #61): SendCampaignJob checked campaign.status.in?(%w[draft scheduled]) and then updated to sending. Two workers that read draft before either wrote sending both mailed the audience. Moving the check and the status write into claim_campaign, under a short campaign.with_lock row lock that is released before the audience query and the SES calls, stopped the double send. This one is a row lock rather than a conditional update: the lock covers one read and one write, and no provider call happens inside it.
    What it taught mePut the precondition in the write itself. A status check in Ruby only tells you what the row looked like a millisecond ago; a conditional UPDATE or short row lock decides ownership without ever holding a database lock across an HTTP call.

    Lease slow provider calls without holding a DB lock ActiveAgent #614 · #715

    A status transition from pending to running solves the start of a job. What about a job that sits in pending while calling an external LLM judge, or a fanned-out replay whose result row does not even exist until the agent answers?

    In ActiveAgent #614, scenario evaluation fan-out already tried to guard EvaluationJudgeJob with a timestamp comparison: where(id: row.id, status: :pending, updated_at: row.updated_at).update_all(updated_at: Time.current). That only rejected a stale reader. A duplicate judge delivery that arrived after the first worker bumped updated_at read the fresh timestamp, bumped it again, and scored the same result a second time.

    A timestamp check only rejects stale readers; a fresh duplicate still runs the LLM twice. Add an expiring ownership token (30-minute lease), release the DB immediately before calling the provider, fence result writes on that token, and re-enqueue losers with wait_until: expires_at so a dead worker is still recovered.

    The fix adds two nullable columns, scoring_token and scoring_expires_at, reworks claim_result!, and adds three short methods: wait_for_claim!, store_claimed_result! and scoring_leases?. The claim and the fenced write:

    def claim_result!(row)
  now = Time.current
  claim = EvaluationScenarioResult.where(id: row.id, status: :pending, updated_at: row.updated_at)
  return claim.update_all(updated_at: now) == 1 unless scoring_leases?

  token = SecureRandom.uuid
  claimed = claim.where("scoring_token IS NULL OR scoring_expires_at <= ?", now)
    .update_all(scoring_token: token, scoring_expires_at: now + JUDGE_LEASE_DURATION, updated_at: now)
  @scoring_token = token if claimed == 1
end

def store_claimed_result!(row, **attributes)
  return row.update!(attributes) unless scoring_leases?

  row.assign_attributes(attributes)
  row.validate!
  EvaluationScenarioResult.where(id: row.id, status: :pending, scoring_token: @scoring_token)
    .update_all(attributes.merge(scoring_token: nil, scoring_expires_at: nil, updated_at: Time.current))
end

    Notice two practical details that matter in real apps. First, both successes and failures are fenced: if a slow worker wakes up after its lease expired and fails, fail_judging! calls the same store_claimed_result! so it cannot overwrite the successor's good score with an error. Second, rolling upgrades stay safe: scoring_leases? checks whether migration 030's columns exist, so a host that upgrades the gem before migrating keeps scoring with the old timestamp check instead of crashing every judge job.

    On 17 November, two and a half weeks later, ActiveAgent #715 applied the same lease design one step earlier, to EvaluationReplayJob itself. There, the result row doesn't exist until the agent finishes, so the lease lives in the run's existing fan-out JSON bookkeeping (scores["_fan_out"]["replays"]), so it needs no migration, and fail_result! only marks a pair errored if this runner actually owns it.

    What it taught meNever hold a database lock across an LLM call, and never leave a failure handler unfenced. A lease token with an expiry separates "who may run" from "how long the network call takes", and fencing both success and error writes stops a zombie worker from corrupting a healthy retry.

    Revalidate intent at claim time, and scope history to the current run Lewsnetter #80 · #82

    A background job does not execute the moment it is enqueued. Between dispatch and execution, users change their minds: they postpone a scheduled campaign, cancel it back to draft, or remove its target segment.

    In Lewsnetter #80, ScheduledCampaignDispatchJob checked that a campaign was due and had a valid audience, then enqueued SendCampaignJob. Once the job ran, it only checked campaign.sendable?, which is true for both draft and scheduled campaigns regardless of scheduled_for. So a queued scheduler job could send a campaign the user had just postponed or pulled back to draft.

    What was true when a job was enqueued may be false when a worker claims it. Carry intent on the job (from_scheduler: true) and re-check all scheduling preconditions under the claim lock (#80); when querying past events, scope them to the current run's timestamp (#82).

    The fix was small and explicit: the dispatcher now passes from_scheduler: true, and inside the existing claim lock SendCampaignJob re-checks the full scheduling contract:

    def scheduler_sendable?(campaign)
  return false unless campaign.scheduled?
  return false if campaign.scheduled_for.blank? || campaign.scheduled_for > Time.current
  return false if campaign.segment_id.nil? && !campaign.all_subscribers_confirmed?

  true
end

    Manual "Send now" clicks and resumes don't pass from_scheduler: true, so they keep working as before. Jobs already sitting in the queue during a deploy default to false and stay backward compatible.

    Lewsnetter #82 caught the mirror image of stale state: looking backwards without a boundary. An automated email sequence checked whether a subscriber had clicked a step's link by querying ClickEvent joined to deliveries by campaign_id and subscriber_id. If that subscriber ever re-entered the sequence, a click from their previous enrollment matched immediately and exited the new enrollment before step 2 ever went out. The fix adds one condition, .where("deliveries.created_at >= ?", since), anchored to the timestamp stamped right before the current enrollment's delivery was created.

    What it taught meEnqueue-time checks are an optimization, not a guarantee. Re-check the caller's intent under the claim lock, and scope every historical lookup to the current run or enrollment, never to "all time for this user".

    Put tool permissions and approvals on the server Lewsnetter #35 · #53 · #54

    When a Rails app gives an AI agent tools, through an in-app chat or an external MCP server, the prompt is not a security boundary. Tool results carry text written by outsiders (subscriber names, email subjects, web pages), so any rule that lives only in the system prompt can be talked past.

    Three pull requests in Lewsnetter moved these rules out of the prompt and onto its 47 MCP tool classes. Two of them enforce the rules on the server; the third describes them to external MCP hosts:

    Never rely on a system prompt to prevent destructive tool calls. Enforce OAuth mcp:read scopes before execution (#35), pause destructive in-app agent calls on the server for explicit human approval (#53), and publish MCP readOnlyHint/destructiveHint annotations for external hosts (#54).

    1. Fail closed on OAuth scopes (Lewsnetter #35): The OAuth consent screen promised that mcp:read could only read team data, but the middleware didn't enforce scopes yet, so a read-only token could call campaigns_delete or campaigns_send_now. Now read-only tools opt in with read_only (24 of 47 tools); every other tool, and every future tool by default, requires write access, and FastMcp's authorize hook refuses disallowed calls with JSON-RPC Unauthorized before the tool runs.
    2. Pause destructive calls on the server (Lewsnetter #53): Four delete tools, sequences_set_enabled, and conditional sequences_update (only when setting status: "active") declare requires_approval. RubyLLM 2.2 saves the call as pending instead of executing it, ActionCable broadcasts an Approve/Decline card with a human-readable summary fetched from the team's own record (Delete campaign "Spring launch" (#12), never a bare ID), and approving re-checks the user's team membership and CanCan ability before executing.
    3. Surface the same metadata to external MCP hosts (Lewsnetter #54): External clients run calls immediately after token consent, so Mcp::Server.tool_annotations translates read_only, destructive, and requires_approval into MCP's readOnlyHint and destructiveHint. It deliberately omits destructiveHint: false on ordinary writes, so nothing claims safety that hasn't been checked. The hints change nothing on the server: every call is still authorized there.
    # app/mcp/tools/sequences/update.rb (Lewsnetter #53)
class Update < Mcp::Tool::Base
  tool_name "sequences_update"
  requires_ability :manage, ::Team
  # An active sequence enrolls and mails subscribers by itself.
  requires_approval { |arguments| arguments["status"] == "active" }

  def approval_summary(arguments:, context:)
    "Activate sequence #{record_label(context.team.sequences, arguments["id"], :name)}: " \
      "it enrolls and sends while Sequences is on"
  end
end
    What it taught meDeclare risk once, on the tool class itself, and fail closed. New tools should require write access until marked read_only, approvals should show the real record name rather than an opaque ID, and hints sent to clients never replace server-side authorization.

    Make evals see what the agent actually called ActiveAgent #665

    The last failure mode is quieter than a double charge, and just as expensive over time: an evaluation suite that looks green while missing half of what the agent did.

    In ActiveAgent #665, Evals::Capture recorded tool calls by wrapping the agent's tools_function. That worked for local Ruby tools, but tools served by a client-side MCP server were dispatched inside BaseProvider#call_tool_function before execution ever reached tools_function. The result: replay.tool_names came back empty for MCP-backed agents, assert_tool_called failed on tools that genuinely ran, and an MCP server returning isError (wrapped in MCPBridge::ErrorResult so the model can recover without raising) left no trace in failed_tool_calls.

    Evals that wrap only local Ruby tool dispatch miss every client-side MCP tool call and silent isError response. Passing a per-instance tool_observer callback into the provider records MCP calls and failures alongside local tools with zero global hooks.

    The fix passed an optional per-instance tool_observer callback from the agent into BaseProvider, wrapping only the bridged MCP branch and feeding both local and MCP calls through the same Capture.record_call helper:

    # lib/active_agent/providers/_base_provider.rb (ActiveAgent #665)
def observe_mcp_tool_call(name, arguments, &call)
  return yield unless tool_observer

  tool_observer.call(name, arguments, &call)
end

    Because the observer lives on the agent instance rather than a global hook or monkey-patch, concurrent evaluation runs never leak records into each other, and ErrorResult payloads are recorded as failed tool calls while still returned unchanged to the model.

    The fix is still the small part

    Across all twelve pull requests there are about 2.5 lines of tests and documentation for every line of application or library code: 2,170 against 854. In my RubyLLM MCP post the ratio was about 4 to 1 (534 against 130). The numbers differ, but the shape holds: the fix is the small part. Every pull request adds tests for the case it fixes, and in eight of the twelve (#664, #665, #672, #713, #715, #35, #53 and #80) the description also reports reverting parts of the fix in turn and seeing a test fail.

    Across the 12 pull requests: 854 lines of application and library code against 2,170 lines of tests and docs (excluding #53's commit from #54's stacked diff). Most of the work is writing deterministic failure tests for overlapping deliveries and edge states.

    Six rules for production Rails + AI workflows

    1. Claim state in the write, not in Ruby. Use a conditional UPDATE ... WHERE status = pending, or a short row lock, so a duplicate delivery declines instead of running twice. (ActiveAgent #664, #672, #713; Lewsnetter #61)
    2. Use expiring leases and fenced writes for slow LLM calls. Never hold a database lock across a provider request, and fence both success and failure writes on the lease token. (ActiveAgent #614, #715)
    3. Revalidate intent when the worker starts. Carry why a job was enqueued (like from_scheduler: true) and re-check the full contract under the claim lock. (Lewsnetter #80)
    4. Scope historical queries to the current run. Never let a prior enrollment or run satisfy a condition for the current one. (Lewsnetter #82)
    5. Keep permissions and approvals on the server, fail closed. Enforce OAuth scopes before dispatch, require human approval with a clear record label on destructive tools, and expose MCP hints honestly. (Lewsnetter #35, #53, #54)
    6. Capture at the real dispatch boundary. If your evals miss client-side MCP tools or silent isError results, your suite is grading a partial trace. (ActiveAgent #665)

    None of these requires a new infrastructure stack. They are ordinary Active Record, Active Job, and authorization habits applied where AI makes mistakes louder and more expensive. If you run a Rails app with background workflows or AI integrations that need this kind of hardening, my open-source record has the full history and my Rails maintenance page explains how I work with teams.

    Limits worth knowing

    Leases prevent ordinary duplicate calls, not true exactly-once remote execution. A worker that crashes right after a provider responds will still be retried after expiry, and provider-hosted MCP tools never pass through your Rails process.

    • Not exactly-once remote calls: In ActiveAgent #614 and #715, a 30-minute lease stops overlapping deliveries, but a provider call exceeding 30 minutes, or a worker dying after the provider answers and before the database write, can still lead to a second call on redelivery.
    • Mid-execution worker death on simple claims: ActiveAgent #664 and #713 leave a run in running if the worker dies after claiming it; recovering stuck runs needs a separate lease or heartbeat sweeper.
    • SQLite transaction semantics differ: As #664 hit on Rails 7.2, a read-then-write under with_lock can raise SQLite3::BusyException on deferred transactions; conditional update_all avoids that, at the cost of handling broadcasts and callbacks explicitly.
    • Backward compatibility during deploys: Both ActiveAgent #614 (checking for migration 030 columns) and Lewsnetter #80 (defaulting missing from_scheduler to false) intentionally degrade gracefully for in-flight jobs queued before the deploy.
    • Hosted MCP tools stay invisible to local capture: ActiveAgent #665 records client-side MCP tool calls (mcp_strategy: :client). Tools executed remotely by a model provider's hosted MCP never enter your Rails process and cannot be observed there.
