After the demo works: five checks for an AI‑built app

Start with payments, access, and the task your users came to do. These public fixes give you five ways to test beyond a successful demo.

01

Webhooks & jobs without idempotency

Retries double-send emails, double-charge, or replay LLM calls when status checks live only in Ruby/JS.

Claim locally. Reconcile uncertain remote effects.
02

Auth & tenant checks in the wrong layer

Hidden UI buttons, system-prompt rules, or missing team_id filters fail when checked only in the client.

Enforce scopes, team_id & approvals on server
03

External APIs & LLMs with no guardrails

Missing timeouts, zombie retries after cancel, or shared outage keys can disrupt a healthy caller.

Explicit timeouts, cancel checks & route keys
04

Dependency drift & real-world edge inputs

Unpatched CVEs, provider API changes, and values like NaN/Infinity need separate upgrade and input tests.

Small tested updates & finite input validation
05

Swallowed errors & zero regression net

Broad rescue/catch blocks hide broken flows, and an HTTP success can carry a tool error.

Track errors and test 3 core paths

The smallest safety net (before you ever consider a rewrite)

Wrap sign-up, billing & core task in integration tests Wire Sentry/Honeybadger and kill silent catch blocks Add idempotency keys, timeouts & server auth checks Run small monthly updates with plain-English notes
